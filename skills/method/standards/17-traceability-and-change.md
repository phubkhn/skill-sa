# Standard 17 — Traceability & Change Management

## Why

An architecture you cannot interrogate is an architecture you cannot safely change. Every element of the design must answer: *what caused you to exist, and what breaks if you change?*

## Trace ID

`<trace-prefix>-<scope>-<NNN>` — prefix from `sa-config.yaml` (default `TR`), scope is the feature/initiative slug, NNN is zero-padded and sequential within scope.

**Origin rule:** a trace-id is minted **once**, at the point where a real-world change enters the system — a new requirement, a change request, an incident, a compliance obligation, or an SA-originated decision with no upstream request. Every artifact produced because of that change **reuses the same id**. Never reissue, never branch the id.

**Next sequence.** `_logs/.trace-index.md` is the authority for the highest allocated id, because it contains only real origin records. Read the last row and increment; start at `001`.

Do **not** derive the next id by grepping the artifact tree — a trace-id quoted in prose, in a changelog, or in a superseded ADR would be counted as allocated. Grep is a fallback only when the index is missing, and if used, the result must be confirmed with the user:

```
grep -rho "TR-<scope>-[0-9]\{3\}" <docs-root> | sort -u | tail -1
```

## Change classification

| Type | Meaning | Requires |
|---|---|---|
| `Initial` | first version of the artifact | — |
| `Update` | refinement or correction inside existing scope | — |
| `Change Request` | new or altered scope driven by a stakeholder ask | `ref: CR-<id>` |
| `Corrective` | change driven by a defect, incident, or review finding | `ref: FINDING-<id>` or `INC-<id>` |

All four values are valid in the artifact header block and in `_logs/.design-log`. The single field `ref` carries the CR / finding / incident id; it is `none` for `Initial` and `Update`.

Classification is decided **once, at origin**, and propagated unchanged downstream. A skill may *propose* a classification from the diff, but the human confirms it — the diff does not know intent.

## Where trace data lives

| Location | Fields |
|---|---|
| Artifact header block (any of the four equivalent formats — Standard 01) | `Trace ID`, `Change Type`, `Ref` |
| `_logs/.design-log` | `trace-id`, `change-type`, `ref`, `delta`, `stale-downstream` |
| `_logs/.trace-index.md` | one row per trace-id → all artifacts it touched |
| ADR | `Trace ID` + `Drivers addressed` |
| Risk register | `Trace ID` of the change that introduced the risk |

## Trace index

`_logs/.trace-index.md` is regenerated by `sa:trace` from `templates/trace-index.md`:

| Trace ID | Origin | Type | Date | Artifacts touched | Status |
|---|---|---|---|---|---|
| TR-checkout-014 | CR-882 "add express lane" | Change Request | 2026-08-09 | intent v3, drivers v2, ADR-0009, container-checkout v4, flow express-lane v1 | In Review |

## Impact query

```
grep -rn "TR-<scope>-<NNN>" <docs-root>
```

Returns every artifact that decision touched, in one command. If an artifact appears in the design but not in any trace, it is **orphaned** — either its origin was never recorded, or it should not exist. `sa:trace --orphans` reports these.

## Staleness propagation

When an artifact changes, its downstream dependents become **stale**, not wrong. The dependency direction is fixed by `00-sa-journey.md`:

| Changed | Becomes stale |
|---|---|
| intent | drivers, impact, options, all designs |
| drivers | impact, options, ADRs, crosscutting designs, cost, review |
| options | ADRs |
| ADR | HLD, deployment view, LLD, interfaces, cost |
| HLD | deployment view, flows, LLD, interfaces, security, cost, review |
| deployment view | resilience, security, cost |
| flow | LLD, resilience, observability |
| LLD | interfaces, data, handoff |
| interface | handoff, any consumer's LLD |
| data | LLD, security, migration plan, cost |
| security | LLD, observability (audit signals) |
| resilience | observability, capacity section of cost, flows (timeout budgets) |
| observability | handoff (definition of done) |
| cost | risk register |
| risk | review |
| review | handoff |

Staleness is recorded in `.design-log` under `stale-downstream` and reported by `sa:trace --stale`. Stale artifacts are not silently regenerated — the SA decides.

**Seed/authority staleness.** Where two steps sit either side of the two-pass rule (Standard 00), the seed artifact becomes stale the moment the authority disagrees with it, even if neither file changed afterwards. `sa:review` reports this as a Major finding, not a warning.
